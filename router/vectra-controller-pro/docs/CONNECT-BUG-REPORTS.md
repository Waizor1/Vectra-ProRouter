# ТЗ для сессии Vectra Connect: баг-репорты роутеров

Сторона бэкенда и админки Vectra Connect (`Vectra_Backend`, пакет `bloobcat`)
для приёма отчётов о сбоях с роутеров Vectra. Роутерная сторона — отдельный
репортёр `vectra-reporter` в репозитории Vectra-ProRouter; решение —
`ProRouter/03 Decisions/ADR-0007-router-bug-reports.md` там же. Правило
владельца про i18n действует: каждая новая строка интерфейса — сразу ru, en
и zh.

## Зачем

Когда софт роутера ведёт себя не так, как задумано (vctl упал, xray
перезапускается по кругу, ядро убило процесс по памяти, роутер
перезагрузился сам, vctl отдал роутер назад и т. п.), роутер сам присылает
короткий отчёт: что случилось, на какой версии, улики (стек, строки
журнала). Мы по нему понимаем и чиним баг. Данных немного и ничего личного:
роутер вычищает ссылки подписки, UUID, ключи, IP/MAC домашних устройств и
посещённые сайты ещё до отправки.

## Что уже есть у вас и что переиспользовать

- **Приём ошибок приложения** — `bloobcat/routes/error_reports.py`
  (`POST /errors/report`, таблица `ErrorReports`): серьёзность, фильтр шума,
  вычистка (`SENSITIVE_KEY_RE` и соседи), лимиты, алерты в Telegram для
  `high`/`critical`. Роутерные отчёты — **тот же пайплайн, отдельный
  источник** (`platform = openwrt`, свой эндпоинт и своя проверка), а не
  вторая система.
- **Проверка роутерного жетона** — ветка `feat/router-ua-token`:
  `bloobcat/services/router_ua.py` (`open_router_ua`, `request_target`,
  `configured_keys`, `registry_from_rows`), реестр ключей устройств
  `bloobcat/db/router_device_keys.py` (миграция 235,
  `scripts/register_router_key.py`), настройки `ROUTER_UA_*`. Формат жетона —
  `internal/uatoken/uatoken.go` в Vectra-ProRouter, эталонная проверка —
  `uatoken.Open`, тест-вектор — `ui/contract/ua-vector.json`.

## Эндпоинт

`POST /errors/router?b=<sha256-hex тела>` на `https://api-app.vectra-pro.net`
(адрес на роутере настраивается, путь — контракт).

Заголовки (те же, что роутер шлёт за подпиской):

| Заголовок | Значение |
|---|---|
| `User-Agent` | `VectraRouter/<версия vctl> vr1.<жетон>` |
| `x-hwid` | HWID роутера, 64 hex (sha256) |
| `x-device-os` | `OpenWrt` |
| `x-device-model` | модель, например `Xiaomi Mi Router AX3000T` |
| `x-ver-os` | выпуск OpenWrt, например `24.10.6` |
| `x-vectra-report-id` | = `reportId` из тела |
| `Content-Type` | `application/json` |

### Проверка (всё до записи в базу)

1. Тело ≤ 64 КБ (иначе 413). `sha256(сырые байты тела)` в hex равно `b`
   из запроса (иначе 400).
2. Жетон из `User-Agent` открывается ключом Vectra (`configured_keys`), из
   него берётся `device id`; по реестру `router_device_keys` находится
   устройство (не отозванное) и его пользователь; подпись сходится для этого
   `x-hwid` и **цели запроса = путь + `?` + сырой query, как их отправил
   роутер** (`/errors/router?b=<hex>`; если прокси перед бэкендом режет
   префикс или переписывает путь — восстановить исходный, как `request_target`
   делает для подписки); время жетона — в окне (`ROUTER_UA_MAX_AGE_DAYS`
   неприменимо: жетон свежий на каждый запрос, окно ±10 мин). Так подпись
   покрывает и тело: подделать отчёт чужого роутера или переиграть старый
   нельзя.
   - `open_router_ua` сейчас ищет устройство по `user_uuid`; для отчёта
     пользователя заранее нет — нужен вариант «найти устройство по `device
     id` из жетона» (тот же код: распечатать → найти запись → проверить
     подпись).
3. Неизвестное устройство, отозванный ключ, неверная подпись — **401**
   (роутер повторит позже: его ключ могут ещё не занести в реестр). Если
   ключи Vectra не настроены — 503.
4. `router.deviceId` в теле не совпадает с `device id` из жетона — **422**.
5. `reportId` уже был от этого устройства — **200 `{"duplicate": true}`**,
   ничего не пишется.
6. Лимит на устройство: 200 отчётов в сутки, дальше **429** с
   `Retry-After`.

### Ответы — и что с ними делает роутер

| Ответ | Роутер |
|---|---|
| 200/201/202 `{"id": "...", "duplicate": false}` | удаляет из очереди |
| 200 `{"duplicate": true}` | удаляет |
| 400 / 413 / 422 | выбрасывает (отчёт битый — повтор бессмыслен) |
| 401 / 403 | держит, повтор раз в 6 ч |
| 404 | держит, повтор раз в час (эндпоинта ещё нет) |
| 429 | ждёт `Retry-After` |
| 5xx, сеть | 1 → 2 → 5 → 15 → 60 мин |

Старше 7 дней роутер выбрасывает сам. Сам роутер не шлёт больше 12 отчётов
в час и 100 в сутки, а одинаковый сбой (тот же `fingerprint`) в течение 6 ч
присылает одним отчётом со счётчиком `count`.

## Тело (schema 1)

```json
{
  "schema": 1,
  "reportId": "0f8d3c2e-6a51-4c1e-9d0b-7f3e2a1c9b44",
  "code": "VCTL_PANIC",
  "severity": "critical",
  "fingerprint": "9c1e…64 hex",
  "title": "vctl упал: panic: runtime error: index out of range [3] with length 3",
  "firstAt": "2026-09-29T21:03:11Z",
  "lastAt": "2026-09-29T21:09:40Z",
  "count": 3,
  "router": {
    "deviceId": "vectra-3f9a0c1d2e4b",
    "model": "Xiaomi Mi Router AX3000T",
    "arch": "aarch64_cortex-a53",
    "openwrt": "24.10.6",
    "vctl": "0.6.0-r19",
    "xray": "26.7.28",
    "reporter": "1.0.0-r1",
    "routeSource": "native",
    "killSwitch": false,
    "uptimeSec": 38207,
    "memTotalMiB": 234,
    "memAvailableMiB": 96
  },
  "evidence": {
    "stack": "panic: runtime error: …\n\ngoroutine 1 [running]:\nmain.(*daemon).… ",
    "log": ["2026-09-29T21:03:10Z vctl: …", "…"],
    "kernel": ["[38201.4] Out of memory: Killed process 2211 (xray) …"],
    "memory": {"topAnonMiB": {"xray": 11, "vctl": 6}, "growing": []},
    "details": {"exitCode": 2}
  }
}
```

- Обязательные: `schema` (= 1), `reportId` (UUID), `code`, `severity`
  (`low|medium|high|critical`), `fingerprint` (64 hex), `title` (≤ 300
  символов), `firstAt`, `lastAt`, `count` (≥ 1), `router.deviceId` (должен
  совпасть с `device id` из жетона), `router.vctl`.
- Остальное — необязательное; неизвестные поля не отвергать (роутер будет
  добавлять факты), но хранить в пределах лимита. `evidence.stack` ≤ 16 КБ,
  `evidence.log` ≤ 80 строк, `evidence.kernel` ≤ 40 строк.
- Всё текстовое на сервере прогнать через ту же вычистку, что и отчёты
  приложения (второй рубеж).
- `evidence.log` — строки системного журнала (`logread`) с тегами
  `vctl[pid]`, `vectra-controller-pro`, `vectra-controller-pro-deadman`,
  `vectra-reporter`, плюс строки procd о службе vctl и строки ядра об
  OOM-убийстве vctl/xray (vectra-reporter 1.0.0-r2).

### Коды

| Код | Серьёзность | Что случилось |
|---|---|---|
| `VCTL_PANIC` | critical | vctl упал (паника Go / fatal error); в `stack` — стек |
| `VCTL_CRASH_LOOP` | critical | vctl падает раз за разом, procd сдался |
| `VCTL_DOWN` | high | vctl включён, но не работал; сторож (дедмен) поднял |
| `DATAPLANE_WITHOUT_XRAY` | critical | правила перехвата стоят, xray нет — сеть дома лежит |
| `XRAY_CRASH` | high | xray завершился не по команде (код выхода, последние ошибки) |
| `XRAY_RESTART_STORM` | high | xray перезапускается по кругу |
| `OOM_KILL` | high | ядро убило процесс из-за нехватки памяти (кого, сколько занимал) |
| `KERNEL_ERROR` | medium | ошибки ядра: page allocation failure, oops, зависание |
| `UNEXPECTED_REBOOT` | high | роутер перезагрузился сам (не плановая в 04:30); аптайм до неё |
| `HANDBACK` | high | vctl вернул роутер старому стеку (PassWall/агенту) — почему |
| `APPLY_REFUSED` | high | xray -test отверг конфиг, который vctl собрал сам |
| `RESCUE_DIRECT` | medium | спасатель перевёл роутер в direct |
| `SUBSCRIPTION_REFUSED` | medium | подписка отвечает тем, что vctl отвергает (заглушка и т. п.) |
| `GEO_REFUSED` | medium | обновление гео-файлов отвергнуто (нет нужных категорий, sha256) |
| `MEMORY_GROWTH` | medium | память растёт при той же нагрузке (утечка или кэш) |
| `REPORTER_ERROR` | low | сбой самого репортёра |
| `MANUAL` | low | клиент нажал «Сообщить о проблеме» (позже; с его комментарием) |
| `TEST` | low | проверочный отчёт (`vectra-reporter test`) — в алерты не идёт |

Новые коды будут появляться: неизвестный код принимать как есть,
показывать сырым.

## Ключ Vectra (`ROUTER_UA_KEYS`)

- Закрытый X25519-ключ Vectra, kid 1: `ROUTER_UA_KEYS=1:<base64 сырых 32
  байт>`, несколько ключей — через запятую (`_parse_keys` в
  `bloobcat/services/router_ua.py`). Значение — только в прод-окружении
  бэкенда, у владельца; ни в одном репозитории его нет.
- Его открытая половина обязана быть
  `77QrxchvI9IzwhHFMVBLuGSk76IhwTovmWI5HKiBgXM=`: это `uatoken.BuiltinKey`
  в vctl и `ROUTER_PUBLIC_KEYS[1]` в бэкенде. Битая запись или чужой ключ
  выключают проверку целиком.
- Роутер запечатывает жетон под ключ, который панель назвала в check-in
  (`claimKey`), иначе под встроенный kid 1. На 2026-09-29 панель ключ не
  называет, так что это kid 1.
- Нет ключа или проверка выключена — `/errors/router` отвечает 503; роутер
  повторяет с отступом и держит отчёты до 7 суток.

## Хранение

- Либо `ErrorReports` с новыми полями, либо своя таблица рядом — на ваш
  выбор, но нужны: `source = router`, `device_id`, `user` (по реестру),
  `code`, `severity`, `fingerprint`, `title`, `vctl`, `xray`, `openwrt`,
  `model`, `first_at`, `last_at`, `count`, `received_at`, `report_id`
  (уникален в паре с `device_id`), `evidence` (JSON).
- **Группировка по `fingerprint`** — это «проблема»: один и тот же сбой с
  20 роутеров — одна строка со счётчиком роутеров и случаев.
- Хранить 90 дней; по одной проблеме — не больше последних 200 отчётов.

## Админка

Раздел **«Роутеры → Сбои»**:

- Список проблем: код, заголовок, серьёзность, сколько роутеров, сколько
  случаев, первый и последний раз, затронутые версии vctl. Фильтры:
  серьёзность, код, версия vctl, устройство/пользователь, период. Сортировка
  по последнему разу.
- Карточка проблемы: отчёты (роутер, пользователь, версия, когда, `count`),
  переход к устройству/пользователю.
- Карточка отчёта: роутер (модель, OpenWrt, версии, аптайм, память),
  заголовок, стек моноширинным блоком, строки журнала и ядра, `details`.
- Отметки «взято в работу / исправлено в версии X»: проблема, которая снова
  пришла с версии новее «исправлено в», — снова открыта.

## Алерты

В Telegram (как `NOTIFY_SEVERITIES` сейчас) — только **новая проблема**
серьёзности `high`/`critical` или **всплеск** (одна проблема с ≥ 5 роутеров
за час), не каждый отчёт. `TEST` — никогда.

## Готово, когда

1. Отчёт роутера (`vectra-reporter test` на тестовом роутере с ключом в
   реестре) принимается, проверяется, виден в «Сбоях», группируется с
   повтором того же `fingerprint`.
2. Тело, изменённое после подписи, отвергается; тот же запрос повторно — 200
   `duplicate`; чужой/неизвестный ключ — 401; `deviceId` не из жетона — 422;
   > 64 КБ — 413; > 200 в сутки — 429.
3. Новая `critical`-проблема даёт одно сообщение в Telegram, повторы — нет.
4. Тесты на всё выше, включая проверку жетона по тест-вектору
   (`ui/contract/report-vector.json` в Vectra-ProRouter — подписанный
   запрос с тестовым ключом; до его появления — по `ua-vector.json` и
   `tests/_router_ua_tokens.py`).
5. Существующий `POST /errors/report` приложения работает как раньше.
