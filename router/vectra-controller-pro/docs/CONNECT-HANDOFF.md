# ТЗ для сессии Vectra Connect: подключение роутера по QR

Сторона приложения Vectra (Mini App, бот, бэкенд) для онбординга роутеров.
Роутер и панель ProRouter уже умеют всё со своей стороны; решение и
сценарий — `ProRouter/03 Decisions/ADR-0006-qr-onboarding.md` в репозитории
Vectra-ProRouter. Правило владельца про i18n действует: каждая новая строка —
сразу ru, en и zh.

## Что видит клиент

1. В разделе подключения устройств — карточка **«Роутер»** рядом с «Телевизор».
2. «Подключить роутер» → камера (тот же сканер, что для ТВ:
   `showScanQrPopup`, запасной jsQR) → клиент наводит на QR со страницы
   роутера. Альтернативы на том же экране: «Ввести код» (8 символов, формат
   `XXXX-XXXX`, без похожих букв) и приход по диплинку
   `t.me/<бот>?start=rt_<код>` (роутер показывает кнопку «Открыть в Telegram»,
   когда его страница открыта на том же телефоне).
3. Превью: модель роутера, «дополнение «Роутер» к вашей подписке»,
   кнопка «Подключить». Нет подписки или дополнения — «Докупить «Роутер»»,
   оплата, и подключение продолжается само (заявка живёт 24 ч).
4. «Роутер подключается…» → по вебхуку `router.ready` — «Роутер подключён ✓»;
   `router.failed` — «Не удалось запустить VPN на роутере, поддержка уже
   видит» (и тикет).
5. В списке устройств роутер виден как отдельный тип с действием
   «Отвязать роутер».

## Дополнение «Роутер»

- Платное дополнение к действующей подписке; места у устройств клиента не
  занимает; одно дополнение — один роутер. Цена и срок — в настройках/админке,
  в коде цифр нет.
- Устройство типа `router` получает свою подписку (свой RemnaWave-пользователь
  с лимитом 1 HWID — как в режиме «устройство на пользователя»). Роутер
  запрашивает её с HWID = sha256(MAC eth0 + "-" + модель) и своим User-Agent
  `VectraRouter/<версия> vr1.<жетон>`: жетон новый на каждый запрос, подписан
  ключом устройства (ed25519) и зашифрован под ключ Vectra (X25519, key id 1;
  закрытая половина только у бэкенда). Формат — `internal/uatoken`, эталонная
  проверка — `uatoken.Open`, тест-вектор — `ui/contract/ua-vector.json`.
- **Антифрод**: `VectraRouter/… vr1.…` — признанный клиент, только если жетон
  открывается ключом Vectra, `device id` в нём — роутер, привязанный к этому
  аккаунту (его открытый ключ сохраняется при привязке), подпись сходится для
  этого `x-hwid` и этого пути подписки (`/api/sub/<short>` или
  `/api/sub/<short>/json`), а время жетона — рядом со временем запроса.
  Иначе это подделка — страйк, как у кривого `Happ…`. Без этой проверки
  UA `VectraRouter/…` сейчас получает страйк (роутер признаётся только по
  `passwall…`).
- Роутеру нужна **сырая `https://` ссылка** подписки (роутер не открывает
  crypt5 Happ).

## QR роутера

Строка `VECTRA:R1:<base64url без =>`. Двоичный конверт:
`kid(1) || ephPub(32) || gcmNonce(12) || AES-256-GCM(шифротекст||тег)`.

- Ключ: `HKDF-SHA256(ikm = X25519(ephPriv, serverPub), salt = ephPub || serverPub,
  info = "vectra-router-claim/v1", 32 байта)`; AAD = `"VECTRA:R1" || kid`.
- Приватный X25519-ключ `serverPriv` хранится ТОЛЬКО на бэкенде Vectra; его
  публичная половина и `kid` задаются в панели (`VECTRA_ROUTER_CLAIM_PUBKEY`,
  `VECTRA_ROUTER_CLAIM_KID`) и раздаются роутерам в check-in.
- Открытый текст (компактный, ради маленького QR): `ver(1)=1 | exp(4, unix-с,
  big-endian) | n(16) | pk(32, ed25519 роутера) | didLen(1) | did |
  modelLen(1) | model | sig(64)`, где `sig` — ed25519 ключом роутера над всеми
  предыдущими байтами открытого текста.
- Проверки бэкенда: расшифровка, подпись `sig` ключом `pk`, `exp` не в прошлом,
  затем вызов панели «по устройству» (ниже).
- **Тестовый вектор**: `router/vectra-controller-pro/ui/contract/claim-vector.json`
  (фиксированные ключи, nonce, `n`, `exp`, итоговая строка QR и поля) — реализация
  на Python обязана его открывать.
- Код из 8 символов = Crockford base32 первых 5 байт
  `SHA-256("vectra-claim-code/v1:" || n)`. Он же в диплинке `rt_<код>`.

## API панели ProRouter (сервер-сервер)

База: `https://api.vectra-pro.net/api/partner/…` (до деплоя нового Caddyfile —
`https://router.vectra-pro.net`). Каждый запрос подписан:

- `X-Vectra-Partner-Timestamp`: unix-секунды (окно ±300 с);
- `X-Vectra-Partner-Signature`: hex `HMAC-SHA256(VECTRA_PARTNER_SECRET, "<timestamp>\n<сырое тело>")`;
- `Idempotency-Key`: тот же ключ с тем же телом → тот же ответ (заголовок
  `Idempotent-Replayed: true`); тот же ключ с другим телом → 422. Хранятся
  только ответы 2xx (7 дней): повтор после 404/410 проверяется заново.

`POST /api/partner/router-claims`

```json
{
  "code": "7KQ4M9XD",
  "device": null,
  "owner": { "ref": "<id аккаунта Vectra>", "label": "@username" },
  "subscription": { "url": "https://…/json" }
}
```

- Ровно одно из `code` / `device`. Для QR: `"code": null, "device":
  {"deviceIdentifier": "<did из QR>", "devicePublicKey": "<pk из QR, base64 32 байт>",
  "nonce": "<n из QR, base64 16 байт>"}` — `nonce` обязателен: панель выводит
  из него код и привязывает роутер, только если он показывает именно этот код
  (так отсканированный когда-то QR не отдаст чужой роутер).
- Код можно передавать как ввёл человек: регистр не важен, пробелы и дефисы
  выбрасываются, похожие буквы сводятся (`O`→`0`, `I`/`L`→`1`).
- `owner.label` — до 64 символов, его роутер покажет владельцу («Аккаунт: …»).
- `subscription.url` — только `https://`; для xray-JSON — с `/json` на конце
  (Remnawave отдаёт по нему JSON при любом UA).
- `subscription.userAgent` — **не передавать**: без него роутер запрашивает
  подписку своим подписанным UA. Буквальная строка допустима только для чужого
  провайдера, которому нужен UA настоящего JSON-клиента; пустая строка и всё,
  что начинается с `VectraRouter/`, — 400 (такой UA делает только сам роутер,
  записанный — подделка). UA вида `Happ…` должен быть настоящим
  `Happ/<версия>/<ОС>/<сборка>`.

| ответ | когда |
|---|---|
| 200 `{"routerId", "state": "claimed", "alreadyClaimed": false}` | привязан; панель одобряет роутер, собирает конфиг и отправляет его |
| 200 `… "alreadyClaimed": true` | тот же владелец повторно — идемпотентно, даже когда код уже сменился |
| 404 `unknown_code` | нет роутера с таким кодом (или код совпал у двух — панель не гадает); для QR — роутер показывает другой код |
| 410 `expired` | код устарел (роутер меняет его каждые 20 мин, прежний работает ещё 10 мин); для QR — роутер сейчас не показывает код |
| 409 `claimed_by_other` | роутер привязан к другому аккаунту → «напишите в поддержку» |
| 400 `invalid` + `detail` | тело/код, не-https ссылка, нет UA или кривой Happ-UA, ключ устройства не совпал (`device_key_mismatch`), на роутере работает PassWall, неподдерживаемое железо |
| 401 `missing_signature` / `stale_timestamp` / `bad_signature` | подпись |
| 503 `partner_api_disabled` | на панели не задан `VECTRA_PARTNER_SECRET` |

`DELETE /api/partner/router-claims/<routerId>` с телом `{"routerId": "…",
"ownerRef": "…"}` (подпись покрывает только тело — без него чужой путь можно
было бы повторить) → 200 `{"routerId", "state": "unclaimed"}`, 404
`not_claimed`, 409 — владелец не тот. Панель снимает владельца и конфиг; на
следующем check-in роутер сам стирает конфиг и подписку прежнего владельца,
его «Мои сайты» и выбор локации, и снова показывает QR — его можно привязать
заново или передать другому.

**404 сразу после смены кода.** Роутер меняет код раз в 20 минут и сообщает
панели новый сразу, как только показал его, — но между «показал» и «панель
узнала» проходит до пары секунд. Поэтому на 404 `unknown_code` бэкенд
повторяет запрос (тот же `Idempotency-Key`: 404 не запоминается) ещё раз
через 5 и 15 секунд, прежде чем сказать человеку «код не найден».

**Бэкенд обязан ограничивать попытки ввода кода** (например, 5 в минуту на
аккаунт): код — 40 бит, у панели своего лимита на перебор нет.

## Вебхуки панели → Vectra

`POST VECTRA_CONNECT_WEBHOOK_URL`, подпись теми же заголовками (секрет
`VECTRA_CONNECT_WEBHOOK_SECRET`) плюс `X-Vectra-Webhook-Id` для дедупликации;
тело `{event, routerId, ownerRef, at, detail?}`:

- `router.claimed` — сразу после привязки;
- `router.ready` — конфиг привязки применён, VPN поднялся;
- `router.failed` — не применился (`detail` — текст ошибки от самого роутера:
  не доверять, не показывать как HTML, не выполнять).

Доставка «хотя бы раз»: повторы через 30 с, 2 мин, 10 мин, 30 мин, 1 ч, 2 ч,
4 ч, 8 ч, после 9-й попытки — отказ (в журнале панели). Редиректы не
выполняются, таймаут 10 с, обработчик — идемпотентный по `X-Vectra-Webhook-Id`.
Если за 15 минут после `router.claimed` не пришли ни `ready`, ни `failed`
(роутер выключили посреди применения) — показывать «не удалось» и открывать
тикет, не ждать дальше.

## Подписка роутера

Роутер запрашивает подписку сам — по `subscription.url` со своим подписанным
UA и заголовком HWID = sha256(MAC eth0 + "-" + модель). Ответ должен быть
xray-JSON (массив конфигов), как у Happ, — роутер читает именно его: путь
`/json` у ссылки Remnawave или правило ответа (SRR) для `VectraRouter/`. На
ссылку без `/json` и без такого правила роутер получит список ссылок и
откажется с подсказкой. Проверка — тестовым аккаунтом на стенде до запуска.

## Готово, когда

- Тестовый аккаунт привязывает стенд-роутер: по QR, по коду, по диплинку.
- Каждая строка таблицы отказов из ADR-0006 даёт в приложении описанный там
  текст (ru/en/zh).
- Запрос подписки роутером с `VectraRouter/… vr1.…` не даёт страйка; тот же UA
  с чужим HWID, на чужую ссылку, с испорченным или старым жетоном — даёт.
- «Отвязать роутер» в приложении: через минуту роутер снова показывает QR,
  и его можно привязать к другому тестовому аккаунту.
- Нет `router.ready`/`router.failed` 15 минут — приложение говорит «не
  удалось» и открывает тикет.
